# Mobile privacy inventory (pre-release)

Flippars does not require a user account in the guest release. The client creates a random installation UUID and a separate 256-bit mutation credential, stores both with iOS Keychain protection, and sends proof only on guest device, preference, and deletion mutations. Public market, signal-history, signal-detail, health, and WebSocket requests do not carry the guest identifier or credential. The API stores only a one-way hash of the mutation credential. The app stores onboarding state, explicit in-app notification opt-in, preferences, recent public signal history, and the latest public market snapshot locally.

The mobile client does not collect contacts, location, advertising identifiers, exchange credentials, financial account details, or trading activity. It does not enable cross-app tracking. A granted iOS notification permission is not treated as Flippars alert consent: the native APNs token is uploaded only after a direct in-app opt-in, and reset returns that opt-in to false.

“Delete/reset anonymous data” first persists an encrypted deletion tombstone, attempts to remove the device record from the API, clears the guest’s local app state, and rotates to a fresh Keychain-protected guest session. If the service is unreachable, the old credential remains in SecureStore and deletion is retried on later live launches and foreground transitions. Pending credentials and their non-secret index are stored as separate Keychain records, so repeated offline resets do not drop an older deletion request or permanently cap local reset.

Operational server logs, retention periods, market-data licensing, the production privacy-policy URL, and App Store privacy labels must be reviewed with backend operations and counsel before public release.
